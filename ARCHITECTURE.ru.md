# Архитектура StonerHand Soundlinks Bot

Документ описывает текущую production-архитектуру Telegram-бота.

> Актуальная схема для релиза 1.11.0. Все пользовательские сценарии сходятся в
> одном конвейере публикации и остаются внутри Telegram.

## Контур системы

```mermaid
flowchart LR
    TG["Telegram"] --> WH["api/telegram.py"]
    WH --> BOT["PTB Application"]
    BOT --> RESOLVE["Resolver и провайдеры"]
    BOT --> EDIT["Черновики и редактор"]
    BOT --> PUB["PublicationService"]
    PUB --> CONTRACT["Final publication contract"]
    CONTRACT --> GW["Telegram API Gateway"]
    GW --> TG
    CRON["Vercel Cron"] --> WORKER["api/queue_worker.py"]
    WORKER --> PUB
    BOT <--> REDIS["Upstash Redis"]
```

Production работает на Vercel Functions. Telegram передаёт updates только через
webhook `/api/telegram`. Polling используется исключительно при локальном запуске.

## HTTP-маршруты

- `/api/telegram` — Telegram webhook;
- `/api/set_webhook` — защищённая регистрация webhook, команд, описаний и меню;
- `/api/health` — Telegram, webhook, Redis, очередь и runtime-метрики;
- `/api/queue_worker` — защищённый cron-tick очереди;
- `/api/collage` — HMAC-подписанный JPEG-коллаж и независимый health-контракт;
- `/api/smoke` — read-only матрица публикаций и ключевых UI/UX-экранов без сети.

- `formatter.py` и `keyboards.py` — единое представление постов.

## Поиск и карточка

Вход классифицируется как текстовый запрос, музыкальная ссылка, YouTube, NTS,
плейлист или артист. Независимые источники обрабатываются параллельно. Успешные
частичные результаты сохраняются даже при ошибке отдельного провайдера.

Одиночный релиз превращается в редактируемую карточку. State machine разделяет
стиль, подводку, хэштеги, площадки, формат Telegram, чистое превью, действия и
планирование. Аудиофайл превращается в тот же черновик с нативной отправкой
`sendAudio`, а пользовательская фотография может заменить обложку релиза.
Свободный текст принимается через нативный Force Reply и сохраняется в сессии,
поэтому cold start не теряет ожидаемый ввод. Перед внешней публикацией бот
показывает короткую сводку с единственной кнопкой подтверждения.
Telegram-entities подводки преобразуются в безопасный HTML без потери жирного,
курсива и внешних ссылок. Музыкальные `text_link`-источники остаются обычным
текстом: их кликабельный URL не дублирует кнопки карточки. Доступный лимит
вычисляется из готового тела публикации и отдельно учитывает UTF-16-лимиты
обычного сообщения и подписи к фото, поэтому эмодзи считаются так же, как на
стороне Telegram.
Любой ожидаемый ввод отменяется командой `/cancel`. До пяти последних изменений
настроек можно последовательно вернуть в течение пяти минут.

Пользовательский интерфейс не показывает внутренний термин «черновик».
Стартовый экран объясняет допустимые входы, поиск остаётся главным действием,
а живая незавершённая карточка доступна отдельной вторичной кнопкой. Перед
показом этой кнопки запись проверяется; устаревший указатель удаляется из
сессии. Для владельца канала публикация видна прямо на карточке, остальные
настройки сгруппированы в конструкторе и обновляют preview в одном сообщении.

Несколько ссылок создают одну подборку. Исходные ссылки и цитата в итоговом
посте не повторяются. Подборку можно назвать и открыть в чистом preview;
дубли не добавляются. Порядок и удаление управляются callback-кнопками,
очистка подтверждается, последнее удаление можно отменить.
Для полной подборки из 2–4 музыкальных релизов Classic preview использует
квадратный коллаж разных обложек. URL источников упакованы в ограниченный
сжатый HMAC-подписанный payload; endpoint принимает только HTTPS, не следует
redirect и ограничивает размер каждого изображения. Неполная подборка и
повторяющиеся обложки сохраняют обычный single-cover preview.

Входные URL извлекаются как из видимого текста, так и из Telegram
`text_link`-entities, затем канонизируются и дедуплицируются с сохранением
порядка. Resolver формирует ровно один `SourceStatus` на каждый уникальный
источник. Полный результат валиден только при совпадении порядка статусов,
числа материалов и числа входов; повреждённый или старый partial-cache
автоматически отбрасывается и пересобирается.
Ссылки разных площадок с совпадающим релизом схлопываются только в presentation
слое: кнопки объединяются, а исходные статусы и возможность точечного retry не
теряются. Публичный плейлист остаётся самостоятельной карточкой, но при наличии
доступных track URL предлагает собрать до десяти позиций в обычную подборку.

## Состояние

| Данные | Redis key | TTL / fallback |
| --- | --- | --- |
| lookup cache | типизированные cache keys | TTL по провайдеру / bounded memory |
| пользовательская сессия | `session:v2:<id>` | 30 дней / bounded memory |
| черновик schema v5 | `draft:<id>` | 48 часов / bounded memory |
| подборка | `bot-crate:v2:<id>` | 14 дней / bounded memory |
| название подборки | `bot-crate-title:v1:<id>` | 14 дней / bounded memory |
| настройки оформления | `channel:template:v2:<hash>` | 180 дней / bounded memory |
| именованные шаблоны | `publication:presets:v1:<hash>` | 365 дней / bounded memory |
| история | `hist:<id>` | 90 дней / bounded memory |
| очередь | `queue:v1` | постоянная / memory fallback |
| антидубли публикаций | `posted:<hash>` | постоянная |
| Telegram media cache | `telegram-media:v1:<hash>` | 30 дней / bounded memory |
| rate limit | `rate:v1:<id>:<window>` | до 61 секунды / bounded memory |

Владение черновиком проверяется по положительному `chat_id`. Callback и update
имеют дедупликацию, а publish/send используют lease, поэтому повторный тап или
повтор Telegram update не создаёт второй пост.
Команда `/privacy` удаляет адресуемые черновики, сессию, историю, подборку,
пользовательские шаблоны, inline-историю, персональные метки статистики и
созданные пользователем задачи очереди. Анонимные общие счётчики сохраняются;
неиндексированные временные selection/retry-токены живут не более 30 минут.

Чтение сессий, подборок и настроек поддерживает предыдущую `v1`: при первом
обращении запись безопасно переносится в актуальную схему без остановки бота.
Пустой окончательный результат кэшируется отдельно только на 3 минуты;
временные ошибки провайдеров в отрицательный кэш не попадают.
Полный результат Song.link хранится 7 дней, а резервная Spotify-карточка —
15 минут: после восстановления агрегатора она быстро заменяется полным набором
площадок. Для Spotify региональный `not found` проверяется в ограниченном наборе
вторичных регионов, затем — по публичным метаданным страницы релиза; ложный
промах повторяется один раз. Неполный результат имеет явный заголовок `N из M`,
не получает кнопку отправки и не попадает в aggregate-cache. Повторная проверка
заново обрабатывает весь исходный набор, поэтому восстановленный материал не
нужно вручную объединять с предыдущей частью. Tracking-параметры не создают
отдельные записи cache/share. Отдельная проблемная позиция может быть заменена
по номеру: retry state хранит исходный порядок, а новый URL подставляется только
в выбранный слот.

## Публикация и очередь

`PublicationService` сначала нормализует текущий или старый durable-черновик в
строгий snapshot, проверяет права и отправляет подготовленный неизменяемый план.
`publication_view` один раз выбирает HTML, итоговую строку хэштегов, клавиатуру,
обложку, link preview и режим доставки для редактора, отправки себе, канала и
очереди, поэтому preview не расходится с итоговым постом. Выключенные в
конструкторе хэштеги не могут быть
неявно включены режимом канала; custom и automatic варианты также разрешаются
ровно один раз в этом слое. Сервис сначала выполняет локальную
preflight-проверку, а готовый результат — общий финальный контракт. Он не
позволяет отправить музыкальную ссылку в тексте, неправильный счётчик partial,
кнопку «Все платформы» не на Songlink/Odesli, search URL, переполненную
клавиатуру или публикацию без обязательной обложки. Загруженное аудио уходит через
`sendAudio`, пользовательская обложка — напрямую по Telegram `file_id` без
повторной загрузки и брендирования. Для обычной карточки пользователь выбирает
Auto с Rich fallback или принудительный Classic. Затем сервис собирает Rich
Message с обложкой, структурированным текстом и кнопками
площадок внутри публикации. Песня и клип используют collage, а подборка —
collage или slideshow. Если новый метод, клиент или конкретное медиа недоступны,
тот же вызов без потери данных переходит на проверенную HTML/photo-карточку.
Inline-публикация выбирает Rich Message только при наличии сохранённого
Telegram `file_id` обложки. Пока такого `file_id` нет, классический путь
намеренно сохраняет крупный link preview и полную клавиатуру, включая
каноническую кнопку Songlink/Odesli; новая возможность API никогда не должна
уменьшать полноту карточки.
Capability cooldown не повторяет заведомо неподдерживаемый запрос на каждом
update, но успешная проба сразу восстанавливает Rich-режим. Сервис записывает
отдельные метрики Rich delivery/error/fallback. Для канала сохраняется компактный
шаблон оформления. Очередь использует статусы `pending` и `processing`, lease,
ограниченные повторы и уведомление владельца при окончательной ошибке.

Worker не зависит от пользовательского интерфейса: он создаёт то же приложение
бота, загружает готовый draft и вызывает общий publication pipeline.
Webhook worker не запускает: пользовательский update не ждёт очередь и не
рискует получить повтор от Telegram из-за чужой долгой публикации. Фиксированные
и пользовательские даты рассчитываются в `BOT_TIMEZONE`; горизонт очереди —
90 дней. При заполнении 50 слотов добавление отклоняется явно, без вытеснения
старой публикации. Экран администратора показывает все слоты постранично и
сохраняет текущую страницу после обновления или отмены элемента.

## Надёжность

- один runtime получает updates: webhook в production, polling локально;
- webhook создаёт приложение лениво и переиспользует соединения на тёплом instance;
- update ID резервируется в Redis до обработки;
- локальная дедупликация защищена от параллельных serverless-вызовов;
- внешние запросы имеют timeout, cache и single-flight;
- музыкальные источники получают собственный timeout после входа в ограниченную
  очередь; запуски сглаживаются, а пяти слотов хватает, чтобы все 10 ссылок
  получили полный шанс в пределах webhook-бюджета;
- ошибки одного провайдера не отменяют найденные материалы, а общий resolver
  проверяет точное соответствие входов, статусов и результатов;
- жанр из Apple Search принимается только при совпадении нормализованных артиста
  и названия релиза; релевантностный результат другой группы не превращается в тег;
- повтор partial-result атомарно пересобирает весь исходный набор;
- этапы прогресса монотонны и не откатываются при повторных callback;
- прогресс позволяет отменить активный поиск, а новый запрос отменяет старый;
- короткое fixed-window ограничение гасит случайный спам до внешних API;
- Telegram-клавиатуры строятся общей семантической фабрикой; PTB 22.8 получает
  нативное поле `style`, а raw-поля остаются только для ещё не типизированных
  возможностей API. Кнопки проверяются контрактными, golden- и snapshot-тестами;
- прогресс использует нативную disabled-кнопку Bot API 10.3 и повторяет отправку
  без неё, если Telegram ещё не поддерживает новый объект;
- ephemeral replies используют вложенный `ephemeral_message_parameters` и
  никогда не мешают публичному fallback;
- повторная photo-публикация использует сохранённый Telegram `file_id`, не
  скачивая неизменившуюся обложку заново;
- runtime агрегирует по каждому провайдеру success rate, среднюю задержку,
  fallback, timeout и rate limit;
- health помечает деградацию площадки отдельно от отказа всего бота, а runtime
  хранит только анонимную воронку `запрос → релиз → изменение → публикация`;
- `BOT_SAFE_MODE=1` одним переключателем отключает Rich, inline Rich, ephemeral
  пути и коллажи, сохраняя проверенный Classic fallback; отдельный
  `COLLECTION_COLLAGE_ENABLED=0` отключает только генерацию коллажей;
- webhook удаляет claim после ошибки, чтобы Telegram мог повторить update;
- профиль, локализованные команды и меню синхронизируются независимо: ошибка
  одного Telegram-вызова не блокирует остальные поля;
- durable draft удаляет неизвестные поля, ограничивает размеры и принимает
  только HTTP(S)-ссылки до создания строгой модели релиза;
- health endpoint параллельно проверяет Telegram, webhook и queue worker,
  считает недоступный worker ошибкой, одним Redis-снимком читает
  очередь/метрики и возвращает version/commit;
- внутренний health-to-worker вызов использует отдельный производный ключ,
  если `CRON_SECRET` сохранён пустым; явный секрет всегда имеет приоритет;
- production canary проверяет реальные API, commit deploy, просроченную очередь,
  сервис коллажей, все финальные форматы и UI/UX-контракт главных экранов;
- ручной checklist закрывает iOS, Android, Desktop/Web, темы и реальные переходы;
- CI выполняет тесты на Python 3.10, 3.11 и 3.12, полный lint, проверку единого
  формата, compile, security-аудит зависимостей и контракт `vercel.json`.
